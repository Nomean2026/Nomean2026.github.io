第 0 章 · 5 min

先回答你的问题：JS 写法还是 TS 写法？@ 包是什么？

你问的 @earendil-works/pi-ai —— 它不是「JS 写的」也不是「TS 写的」，它是一个 npm 包名。想搞清楚它，只需要先搞懂三件事：JS 和 TS 的关系、npm 的命名规则、import 的语法。这一章先把前两件说清楚，import 语法下一章专门讲。

0.1 JS 和 TS 到底什么关系？

一句话：TS = JS + 类型系统。TS 是 JS 的超集，所有合法的 JS 代码都是合法的 TS 代码。它们的区别，恰好就是你熟悉的 Python 和 C 的区别：

维度JavaScriptTypeScript像什么
类型检查运行时（动态类型）编译期（静态类型）JS 像 Python，TS 像 C
谁在执行浏览器 / Node.js先被转译成 JS，再执行TS ≈ C 编译成机器码，但转译目标是 JS
文件后缀.js.ts—
写代码的体验随便写，错了运行时才知道写的时候就有类型提示和报错TS ≈ 给 JS 加上了 gcc 的 -Wall
关键事实 浏览器和 Node 只认识 JS。TS 是给开发者写的，写完必须转译成 JS 才能运行。所以一个项目里往往同时有 .ts（源码）和 .js（产物）。你工作区里的 obsidian-outline-sidebar 就是活例子：main.ts 是源码，main.js 是构建产物，Obsidian 插件实际加载的是 main.js。

0.2 import 语法在 JS 和 TS 里一样吗？

一样。因为 TS 是 JS 的超集，import/export 语法是两者共用的。区别只在：TS 在导入时能拿到包自带的类型声明（.d.ts 文件），编辑器会给你补全和报错提示；JS 拿不到。但语法本身，完全一样。

0.3 @earendil-works/pi-ai 是什么？

它是 npm 上发布的一个包，名字格式是 @作用域/包名：

  • @earendil-works —— 作用域（scope），相当于一个命名空间，通常是一个组织或用户名。类比：GitHub 的 用户名/仓库名。
  • pi-ai —— 包名，这个组织里的具体包。
  • 安装：npm install @earendil-works/pi-ai
  • 使用：import { ... } from '@earendil-works/pi-ai'

想看它到底导出什么、怎么用？两个办法：看它的官方文档；或者装到本地后，打开 node_modules/@earendil-works/pi-ai/ 目录，读它的 package.json（入口在哪）和类型声明文件（导出了哪些名字）。第 3 章讲完 npm，你就能完全读懂。

本课程的三句总纲 JS = 动态类型 + 解释执行（像 Python），跑在浏览器/Node。
TS = JS + 编译期类型检查（像 C 的编译期检查）。
npm = pip；package.json ≈ pyproject.toml；node_modules ≈ site-packages。
检查一下：TS 比 JS 多了什么？
多了编译期的静态类型系统。写 .ts，用 tsc / esbuild 等工具转译成 .js 再运行。运行时跑的都是 JS。
第 1 章 · 12 min

思维映射：把 Python/C 的知识平移过来

这一章不做「Hello World 大全」，只讲差异。你已有的概念（变量、函数、dict、list、作用域、闭包）在 JS 里几乎都存在，只是换了写法。

1.1 变量：let / const，块级作用域

Python
# 变量随时可以重新绑定
count = 0
count = count + 1   # OK

PI = 3.14
PI = 3.0            # 也 OK（大写只是约定）
→
JavaScript
let count = 0;        // let：可变
count = count + 1;    // OK

const PI = 3.14;      // const：不可重新赋值
PI = 3.0;             // ❌ TypeError

const 的意思是「这个名字只能绑定一次」，和 C 里 const 变量的语义一致。注意：const 只禁止重新赋值，不禁止修改对象内部（下面讲对象时你会看到）。JS 的惯例是：默认用 const，确实要改才用 let。

1.2 作用域：JS 的 {} 和 C 一样是块级

Python
# Python 没有块级作用域
if True:
    x = 1
print(x)   # 1，if 外面也能访问
→
JavaScript
// JS：let/const 是块级作用域
if (true) {
  let x = 1;
}
console.log(x);   // ❌ ReferenceError

这对你来说是零成本知识：C 的 if/for 的 {} 就是块级作用域，JS 的 let/const 和 C 完全一致。老代码里的 var 是函数级作用域（近似 Python 的行为），现在写新代码用 let/const，避开 var 的坑。

1.3 类型：动态（JS）→ 注解（TS）

JavaScript（动态）
let x = 42;       // 数字
x = "hello";      // 换成字符串，合法
                  // 类型是运行时才知道的
→
TypeScript（静态）
let x: number = 42;
x = "hello";
// ❌ 编译错误：
// string 不能赋给 number
// 这就是 C 的体验
JS/TS 类型Python 对应说明
numberint / floatJS 不分 int/float，全是 64 位浮点
stringstr单引号、双引号、反引号都能写字符串
booleanbooltrue / false（注意小写）
null / undefinedNone两个「空」：null 是你主动设的空，undefined 是「还没赋值」
object / arraydict / list对象字面量 ≈ dict，数组 ≈ list
function函数一等公民，可当参数传

1.4 函数与箭头函数 ≈ lambda

Python
def double(x):
    return x * 2

double_l = lambda x: x * 2
→
JavaScript
function double(x) {
  return x * 2;
}

const doubleL = (x) => x * 2;
// 箭头函数 ≈ lambda

函数可以当参数传、可以存进变量 —— 和 Python 一样。这在 JS 里叫回调（callback），后面你会天天见到：arr.map(x => ...) 里的箭头函数就是回调。

1.5 字符串模板 ≈ f-string

Python
name = "Alice"
print(f"Hello, {name}!")
→
JavaScript
const name = "Alice";
console.log(`Hello, ${name}!`);
// 反引号 + ${} = 模板字符串

1.6 对象字面量 ≈ dict

Python
person = {"name": "Alice",
          "age": 30}
print(person["name"])   # Alice
→
JavaScript
const person = {
  name: "Alice",
  age: 30,
};
console.log(person.name);      // Alice
console.log(person["name"]);   // 也行

1.7 数组方法 ≈ 列表推导

Python
nums = [1, 2, 3, 4]
doubled = [x * 2 for x in nums]
evens = [x for x in nums
         if x % 2 == 0]
→
JavaScript
const nums = [1, 2, 3, 4];
const doubled = nums.map(x => x * 2);
//            [2, 4, 6, 8]
const evens = nums.filter(
  x => x % 2 === 0);      // [2, 4]

对照关系：map ≈ 推导式主体；filter ≈ 推导式的 if 条件；reduce ≈ 累积（Python 的 functools.reduce）。注意 JS 用 === 严格相等，别用 ==（它做类型转换，是经典坑）。

1.8 闭包：和你 Python 里学的一样

JS 的作用域是词法作用域（按代码结构决定，不看调用位置）—— 和 C、Python 一致。闭包 = 函数 + 它记住的外层变量：

closure.jsJavaScript
function makeCounter() {
  let n = 0;
  return () => { n += 1; return n; };
  // 内层箭头函数"记住"了外层变量 n
}

const c = makeCounter();
c(); c(); c();   // 1, 2, 3 —— n 不会被回收
JS 独有的坑：this 你懂 C 和 Python，这里只需记住一条：this 的值取决于"函数怎么被调用"，不像 Python 的 self 固定是第一个参数。而箭头函数没有自己的 this，它会继承外层作用域的 this。所以写回调时优先用箭头函数，能避开 90% 的 this 坑。第一周记住这一条就够了。
本章小结
  • const 不可重新赋值、let 可变、默认用 const —— 对应 C 的 const 语义
  • let/const 是块级作用域，{} 就是边界 —— 和 C 一样，和 Python 不同
  • 箭头函数 (x) => x * 2 ≈ lambda；模板字符串 `${x}` ≈ f-string
  • 对象字面量 ≈ dict；map/filter ≈ 列表推导；闭包概念和 Python 相同
  • 相等判断永远用 ===
let 和 const 的区别是什么？
let 声明的变量可以重新赋值；const 声明的名字只能绑定一次（但对象内部内容仍可修改）。两者都是块级作用域。
第 2 章 · 15 min

模块与导入导出：import / export 全解

这是你问得最具体的地方。好消息：Python 的 import 你早就会了，JS 只是换了个语法。核心就三条映射，记住就通关。

2.1 三条最重要的映射

PythonJavaScript / TypeScript（ESM）
import mathimport * as math from 'math'（整体导入）
from math import sqrtimport { sqrt } from 'math'（命名导入）
from math import sqrt as sqimport { sqrt as sq } from 'math'（别名）
—（Python 没有默认导出）import main from './main'（默认导入）

2.2 命名导出 vs 默认导出

先看「被导入的文件」怎么写导出（export）：

mathUtils.tsTypeScript
// 命名导出：一个文件可以导出一大堆名字
export function add(a: number, b: number): number {
  return a + b;
}
export const PI = 3.14159;

// 默认导出：每个文件最多一个"主角"
export default function main() {
  // 入口逻辑
}

再看「导入方」怎么用（import）：

app.tsTypeScript
import { add, PI } from './mathUtils';      // 命名导入：名字必须对上
import { add as plus } from './mathUtils';  // 起别名：plus === add
import * as utils from './mathUtils';       // 整体导入：utils.add(...)
import main from './mathUtils';             // 默认导入：名字随便起

console.log(add(1, 2));        // 3
console.log(utils.PI);         // 3.14159
main();
直觉 默认导出 ≈ 一个模块只有一个「主角」（比如单函数模块）；命名导出 ≈ 模块里每个公开的名字。默认导入时花括号可有可无、名字随便起；命名导入必须有花括号、名字必须和导出时一致。
路径规则：./ 开头 vs 裸包名 ./ 或 ../ 开头 = 相对路径，导入你自己写的文件；裸包名（如 '@earendil-works/pi-ai'、'obsidian'）= 去 node_modules/ 里找包。这是新手最容易混的地方：看到 ./ 就是本地文件，没有 ./ 就是第三方包。

2.3 CommonJS：Node 的老写法（你也会遇到）

2015 年之前 Node.js 只有 CommonJS 这一种模块系统，语法是 require / module.exports。现在的新代码用 ESM（import/export），但你会经常在旧项目、工具脚本里看到 CommonJS，认得就行：

CommonJS（老）
// 导入
const utils = require('./mathUtils');
const { add, PI } = require('./mathUtils');

// 导出
module.exports = { add, PI };
↔
ESM（新）
// 导入
import * as utils from './mathUtils';
import { add, PI } from './mathUtils';

// 导出
export { add, PI };

为什么有两种？历史原因：浏览器原生支持 ESM（<script type="module">），而 Node 在 2015 年之前只有 CommonJS，后来才逐步支持 ESM。一个 .js 文件按哪种解析，由 package.json 里的 "type": "module" 决定（没有这行就是 CommonJS）。

实操建议 你写代码时统一用 import/export 就行，转译工具（tsc、esbuild、Vite）会帮你转成目标环境需要的格式。比如你的 Obsidian 插件项目，esbuild 配置里写了 format: "cjs"，就是把源码里的 import 转成 CommonJS 输出 —— 你不用自己操心。

2.4 完整例子：从零写两个文件

greetings.ts
export function hello(name: string): string {
  return `Hello, ${name}!`;
}

export default function hi() {
  return "Hi!";
}
→
app.ts
import { hello } from './greetings';
import hi from './greetings';

console.log(hello("Alice"));  // Hello, Alice!
console.log(hi());            // Hi!

运行方式：浏览器里用 <script type="module" src="app.js"></script>；Node 里跑转译后的 .js 文件（比如 node app.js）；TS 文件则先经工具转译。这一节你只要懂「导出什么、导入什么」，运行细节交给工具。

本章小结
  • from math import sqrt → import { sqrt } from 'math'；import math → import * as math from 'math'
  • 导出用 export（命名）/ export default（主角）；导入用 import，命名导入要花括号
  • ./ 开头是本地文件，裸包名是 node_modules 里的包
  • 看到 require/module.exports = CommonJS 老写法；import/export = 现代 ESM
写出 from math import sqrt as sq 对应的 TS 写法
import { sqrt as sq } from 'math';
import { add } from './utils' 里的 ./ 是什么意思？
相对路径，表示 utils 是你自己写的本地文件（同目录下）。不带 ./ 的裸包名才是去 node_modules 找第三方包。
第 3 章 · 15 min

npm：Node 世界的 pip

npm 是你已经会的东西（pip）换了个名字和语法。这一章把每个概念对应起来，再用你的真实项目逐字段解剖 package.json。

3.1 概念对照表

概念Python 世界Node 世界
包仓库PyPI（pypi.org）npm registry（registry.npmjs.org）
安装命令pip install xxxnpm install xxx（简写 npm i xxx）
依赖清单requirements.txt / pyproject.tomlpackage.json 里的 dependencies / devDependencies
依赖实体装在哪venv 的 site-packages项目根目录的 node_modules/（每个项目一份）
锁定精确版本pip freeze > requirements.txtpackage-lock.json（自动生成，提交 git）
项目元数据 + 脚本pyproject.toml + Makefilepackage.json 的 name/version + scripts
本地开发安装pip install -e .npm link 或 file: 依赖

3.2 package.json 解剖（用你的真实项目）

这就是你工作区里 obsidian-outline-sidebar/package.json 的原样内容：

obsidian-outline-sidebar/package.jsonJSON
{
  "name": "obsidian-outline-sidebar",   // 包名（发布到 npm 时用）
  "version": "1.1.0",                   // 版本：主版本.次版本.补丁
  "main": "main.js",                    // 入口：别人 import 这个包时加载的文件
  "scripts": {                          // 自定义命令：npm run 后面跟的名字
    "dev": "node esbuild.config.mjs",           // 开发：监视 + 自动重新打包
    "build": "tsc -noEmit -skipLibCheck && node esbuild.config.mjs production"
  },                                    // 构建：先类型检查，再打包
  "devDependencies": {                  // 只在开发/构建时用的依赖
    "@types/node": "^16.11.6",          // Node API 的类型声明
    "esbuild": "0.17.3",                // 打包器（把 TS 转成 JS 并合并）
    "obsidian": "latest",               // Obsidian API 的类型
    "typescript": "4.7.4"               // TS 编译器
  }
}
  • name / version：包的身份标识。要发布到 npm 时，别人就用 npm install obsidian-outline-sidebar 装它。
  • main：入口文件。相当于 Python 包里的 __init__.py 指向的模块。
  • scripts：≈ Makefile 里的目标。运行 npm run build 就执行 build 那一行的命令。
  • dependencies：程序运行必需的包；devDependencies：只有开发/构建时才需要的包（编译器、打包器、类型声明都属于这类）。
怎么区分两类依赖？ 问自己：这个包是「用户跑我的程序时需要」还是「只有我写代码/构建时需要」？前者进 dependencies（如 Web 框架），后者进 devDependencies（如 typescript、esbuild、测试框架）。装包时用 npm i xxx（默认进 dependencies）或 npm i -D xxx（进 devDependencies）。

3.3 node_modules 和 package-lock.json

  • node_modules/：依赖的实际文件，≈ venv 里的 site-packages。不提交 git（.gitignore 里排除），别人 clone 后执行 npm install 重新生成。
  • package-lock.json：记录精确的版本树（每个依赖的依赖也锁定），≈ pip freeze 的完整快照。要提交 git，保证任何人 npm install 得到一模一样的版本。

3.4 @scope/name：作用域包

回到你的问题 —— @earendil-works/pi-ai 就是一个作用域包：

terminalShell
# 安装（会写进 package.json 的 dependencies）
npm install @earendil-works/pi-ai

# 查看包的信息（版本、描述、依赖）
npm view @earendil-works/pi-ai

# 使用：裸包名导入，不用写 ./ 路径
import { something } from '@earendil-works/pi-ai';

规则：@ 后面的 earendil-works 是作用域（组织/用户名），/ 后面的 pi-ai 是包名。作用域的作用是防止重名：全世界的包都叫 utils 会撞车，但 @earendil-works/utils 是唯一的。类比：PyPI 的包名是全局唯一的（如 requests），npm 用 @组织/包名 提供命名空间。安装后它出现在 node_modules/@earendil-works/pi-ai/ 目录下 —— 打开这个目录，读它的 package.json（exports 字段声明了导出了什么）和 .d.ts 类型声明，你就能完全搞清楚这个包怎么用。这是「读懂任何陌生包」的通用方法。

3.5 版本号：^ 和 ~ 是什么意思

版本号是 主版本.次版本.补丁（如 1.2.3）。npm 安装时默认给你带 ^：

写法允许的更新范围类比
^1.2.3≥1.2.3 且 <2.0.0（大版本内随便升）npm 默认，最常用
~1.2.3≥1.2.3 且 <1.3.0（只升补丁）保守
1.2.3精确锁定最严格

为什么关心这个？主版本 0（如 0.x）意味着 API 随时可能变；升到 1.0 才承诺向后兼容。看到 ^0.5.0 这种，升级时就要小心 API 变化。

3.6 常用命令速查

terminalShell
npm init -y          # 生成一个新的 package.json（≈ 初始化项目）
npm install          # 按 package.json 装全部依赖（clone 项目后第一步）
npm install xxx      # 装包 + 写入 dependencies
npm install -D xxx   # 装包 + 写入 devDependencies
npm uninstall xxx    # 卸载
npm run <script>     # 执行 package.json 里 scripts 定义的命令
npx xxx              # 临时运行某个包的命令，不必先安装（如 npx tsc）
npm view xxx         # 查看包的信息（不进 node_modules）
本章小结
  • npm = pip；node_modules = site-packages；package.json = 项目身份证；package-lock.json = 精确版本快照
  • dependencies = 运行必需；devDependencies = 开发/构建工具
  • @earendil-works/pi-ai = 作用域包，@后面是组织/命名空间
  • ^1.2.3 允许大版本内更新；npm run build 执行 scripts 里的命令
typescript、esbuild 这类工具应该放 dependencies 还是 devDependencies？
devDependencies。它们是开发/构建时才需要的工具，用户运行你的程序时并不需要。
第 4 章 · 12 min

TypeScript：像 C 一样在编译期抓错

你已经会 C 的类型声明，TS 就是给 JS 加上同样的东西。这一章很短，因为概念你全懂，只是换语法。

4.1 工作流：写 .ts → 编译成 .js

terminalShell
npm install -D typescript   # 装编译器 tsc
npx tsc --init              # 生成 tsconfig.json（≈ 编译选项配置）
npx tsc                     # 按 tsconfig.json 编译 .ts → .js

对照：tsc ≈ gcc/clang；tsconfig.json ≈ 编译选项（Makefile/CMake 的配置）。实际工程里常不用 tsc 直接编译，而是用 esbuild 等打包器（更快），但类型检查还是 tsc 在做 —— 你的插件项目 build 命令就是 tsc -noEmit（只查类型不输出）再接 esbuild 打包。

4.2 类型注解：和 C 的声明一样

TypeScript
let age: number = 30;
const name: string = "Alice";
let flag: boolean = true;
let list: number[] = [1, 2, 3];
let maybe: string | null = null;

function add(a: number, b: number): number {
  return a + b;
}
≈
C（示意）
int age = 30;
char *name = "Alice";
int flag = 1;
int list[3] = {1, 2, 3};

int add(int a, int b) {
  return a + b;
}

语法不同、精神相同：编译期检查。TS 编译后类型信息会被擦除，运行时就是纯 JS —— 所以类型检查零运行时开销，这和你 Python 里用 mypy 是一个思路。

4.3 类型推断：能省则省

inference.tsTypeScript
let x = 5;        // TS 自动推断 x 是 number，不用写
const y = "hi";   // y 推断为 "hi"（字面量类型）
let z;            // 没赋值也没注解 → 类型是 any（能不开这个口就别开）

TS 的推断能力很强，很多地方不用手写类型。打开 "strict": true（tsconfig 里），它会在编译期拦住一大类 bug（比如对可能是 null 的值做运算）—— 这就是 TS 最大的价值：把 C 编译器能抓的错误，提前到写代码时抓。

4.4 interface ≈ struct

TypeScript
interface Person {
  name: string;
  age: number;
}

const alice: Person = {
  name: "Alice",
  age: 30,
};
≈
C
typedef struct {
  const char *name;
  int age;
} Person;

Person alice = {"Alice", 30};

区别在于 TS 的 interface 是结构类型（鸭子类型）：只要形状对就行，不需要显式声明「我实现了 Person」—— 和 Python 的鸭子类型一个味道，只是检查发生在编译期。

4.5 泛型 ≈ C++ 模板 / Python 的 TypeVar

generic.tsTypeScript
function first<T>(arr: T[]): T {
  return arr[0];
}

first([1, 2, 3]);    // 这里 T 自动 = number
first(["a", "b"]);   // 这里 T 自动 = string

4.6 类型从哪来？

  • 你自己写：interface / type 定义。
  • 包自带：库发布时带上 .d.ts 类型声明（TS 写的库直接就有；JS 写的库可能有社区维护的声明）。
  • @types/xxx：社区维护的类型声明包，比如你项目里的 @types/node（给 Node 内置 API 提供类型）。

对照 Python 生态：.d.ts ≈ .pyi stub 文件，@types ≈ typeshed。

本章小结
  • TS = JS + 编译期类型检查；写 .ts，工具转译成 .js 再运行
  • x: number 注解 ≈ C 的声明；interface ≈ struct（但按形状匹配）
  • 联合类型 string | null、泛型 <T> ≈ 模板
  • 开 strict 模式，让编译器帮你抓错
interface 和 C 的 struct 有什么本质区别？
struct 是名义类型（必须是同一个 struct 类型）；TS 的 interface 是结构类型——只要字段形状匹配就算数，像 Python 的鸭子类型，但检查发生在编译期。

真实项目解剖：你的 Obsidian 插件

理论讲完，现在解剖你工作区里那个真实项目 obsidian-outline-sidebar —— 它麻雀虽小、五脏俱全。

obsidian-outline-sidebar/目录
obsidian-outline-sidebar/
├── package.json        # 项目身份证：名字、版本、依赖、scripts
├── tsconfig.json       # TS 编译配置（module、target、strict 等）
├── esbuild.config.mjs  # 构建脚本：esbuild 打包配置（.mjs = ESM 格式的 Node 脚本）
├── manifest.json       # Obsidian 插件清单（插件 ID、版本、描述）
├── main.ts             # 源码入口 —— TS 写的，人看的
├── main.js             # 构建产物 —— JS，Obsidian 实际加载的
├── styles.css          # 插件样式
└── node_modules/       # 依赖实体（不提交 git）

5.1 一次 build 发生了什么？

在项目里执行 npm run build，等价于执行 scripts 里定义的那一行：

terminalShell
tsc -noEmit -skipLibCheck && node esbuild.config.mjs production
# ①  tsc 做类型检查（-noEmit：只检查、不输出文件）
# ②  通过后 esbuild 把 main.ts 打包成 main.js
#     （external 的 obsidian/electron 等不打进去，运行时由宿主提供）

这就是「TS 最终跑起来是 JS」的完整现场：main.ts 是给人写的，main.js 是给机器跑的。开发时用 npm run dev，esbuild 会监视文件变化自动重新打包。

5.2 为什么 esbuild.config.mjs 里写 format: "cjs"？

因为 Obsidian 的插件加载器用的是 CommonJS 环境。所以 esbuild 把源码里的 import 转成 require 输出 —— 这正是第 2 章说的「你写 import，工具帮你转格式」。external 列表里的包（obsidian、electron、@codemirror/...）不打包进 main.js，运行时由 Obsidian 提供，避免重复打包。

5.3 典型 TS 项目的通用结构

一个更典型的项目目录
my-app/
├── src/              # 源码（.ts），大项目习惯都放这里
│   ├── index.ts      # 入口文件
│   └── utils.ts
├── dist/             # 构建产物（.js），永远不要手改
├── tests/            # 测试
├── package.json      # 依赖 + scripts
├── tsconfig.json     # 编译配置
└── node_modules/     # 依赖（不提交 git）

小项目（如你的插件）可以入口直接放根目录；大项目统一 src/ 放源码、dist/ 放产物。无论大小，package.json + tsconfig.json + node_modules 这三件套一定在。

动手实验（强烈建议） 打开 obsidian-outline-sidebar 项目，执行 npm install（生成 node_modules），再 npm run build（先生成 main.js 再重新打包）。然后改一行 main.ts 里的字符串，再 build 一次，看 main.js 里对应位置跟着变 —— 你就亲眼看到了「TS 源码 → JS 产物」的完整链路。

异步编程：async / await，和 Python 几乎一样

如果你用过 Python 的 asyncio，这一章 2 分钟就能看完 —— 概念完全同构。

Python
import asyncio

async def fetch():
    await asyncio.sleep(1)
    return "data"

data = await fetch()
≈
TypeScript
async function fetchData(): Promise<string> {
  await sleep(1000);      // Promise 版的 sleep
  return "data";
}

const data = await fetchData();
  • Promise ≈ Python 的 Future：一个「将来才有结果」的容器。函数声明 async 后返回值自动包成 Promise。
  • await 的语义和 Python 一模一样：挂起当前函数，等异步操作完成。
  • JS 是单线程 + 事件循环（≈ Python 的 asyncio 事件循环）。Node 的 IO、浏览器的 fetch（网络请求）都是异步的，所以你会经常见到 await。
  • 遇到 .then(x => ...) 老写法别慌，它 ≈ future.add_done_callback(...)，用 await 更现代。
记忆点 async 函数里才能用 await；await 后面跟一个 Promise；看到 .then / .catch 就是 Promise 的回调风格写法。
